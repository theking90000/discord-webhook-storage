# Discord webhook storage

Use Discord webhooks as file storage. Store files up to 20 MB and retrieve them
with Range support and signed URL renewal included.

## Installation

In `Cargo.toml`:

```toml
[dependencies]
discord-webhook-storage = "0.1.0"
```

## Basic usage

The caller establishes a TLS connection to `discord.com:443` and supplies a
transport implementing `futures::AsyncRead`, `futures::AsyncWrite`, and `Unpin`.

```rust,no_run
use discord_webhook_storage::{Result, WebhookCredentials, WriteConfig, WriteFile};
use futures::{AsyncRead, AsyncWrite, AsyncWriteExt};

async fn upload<T>(connection: T, webhook_url: &str) -> Result<()>
where
    T: AsyncRead + AsyncWrite + Unpin,
{
    let credentials = WebhookCredentials::parse(webhook_url)?;
    let mut file = WriteFile::open(
        connection,
        &credentials,
        &WriteConfig::default(),
    )
    .await?;

    file.write_all(b"hello from Rust").await?;
    let uploaded = file.finish().await?;
    println!("{}", serde_json::to_string(&uploaded)?);
    Ok(())
}
```

The included `webhook_upload` example establishes TLS with `tokio-tcp-pool`
and uploads 20,000,000 generated bytes:

```sh
DISCORD_WEBHOOK_URL='https://discord.com/api/webhooks/<id>/<token>' \
    cargo run --example webhook_upload --features tokio-tcp-pool
```

The optional `tokio-tcp-pool` feature enables the dependency used by this example.
The library accepts caller-supplied transports with or without this feature.

## Upload lifecycle and limits

- `WriteConfig::default()` uses `file.bin` and allows 20,000,000 file bytes.
  These are the crate's defaults; the server may enforce a different limit.
  Configuration fields currently have no public setters.
- A write whose buffer exceeds the remaining payload allowance fails before
  sending that buffer. Smaller writes can still use the remaining allowance.
- `flush()` sends buffered data. `close()` completes the request body while
  keeping the transport open for the response.
- `finish()` completes the request, reads the response, and consumes the writer
  and connection. Dropping an unfinished writer does not complete the upload.
- Responses must use HTTP/1.1 with `Content-Length` or chunked transfer encoding.
  Decoded response bodies are limited to 16 KiB, and a successful upload requires
  status 200, a message identifier, and a first attachment URL.

`WrittenFile` serializes as an object with `id` and `url` string fields. It also
supports deserialization; its fields currently have no public accessors.
